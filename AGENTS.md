AGENTS.md for sml-develop

Purpose
- This file contains instructions and conventions for agentic coding agents working in this repository.
- It documents build/test commands, how to run a single test, recommended lint/formatting guidance, and code-style rules.

Quick commands
- Run all tests: `./gradlew test`
- Run a single test class: `./gradlew test --tests "be.endevops.ApplicationTest"`
- Run a single test method: `./gradlew test --tests "be.endevops.ApplicationTest.testRoot"`
- Build project: `./gradlew build`
- Run the server locally: `./gradlew run`
- Build a fat/executable JAR (project-provided task): `./gradlew buildFatJar`
- Build container image (project-provided task): `./gradlew buildImage`
- Publish image locally (project-provided task): `./gradlew publishImageToLocalRegistry`
- Run via Docker (project-provided task): `./gradlew runDocker`

Notes about tests
- The project uses Kotlin/JVM tests and Ktor test utilities (see `src/test/kotlin/ApplicationTest.kt`).
- Gradle's `--tests` filter works for package/class/method filtering. Use fully-qualified names for predictable results.
  - Examples:
    - Class: `./gradlew test --tests "be.endevops.ApplicationTest"`
    - Method: `./gradlew test --tests "be.endevops.ApplicationTest.testRoot"`
- To debug tests in IntelliJ: open the test class and use the IDE run/debug icons.

Linting & formatting
- There is no enforced linter/formatter plugin configured in this repository. Gradle properties set `kotlin.code.style=official` (see `gradle.properties`).
- Recommended (optional) setup for consistency across contributors/agents:
  - Add `ktlint` or `detekt` for styling/linting rules, and `spotless` or `ktfmt`/`ktlint` for formatting if you want automated checks.
  - Common commands (after adding the relevant plugins):
    - `./gradlew ktlintCheck` or `./gradlew detekt` (lint checks)
    - `./gradlew ktlintFormat` or `./gradlew spotlessApply` (autoformat)
- For agentic edits: format Kotlin with `ktfmt`/`ktlint` rules or run IntelliJ Kotlin formatter settings to match `kotlin.code.style=official`.

Repository-specific build notes
- The repository was generated by Ktor. Useful tasks are listed in `README.md` and available via the Gradle wrapper in the repository root.
- Use the included wrapper `./gradlew` to ensure consistent Gradle tooling across environments.

Code style guidelines
These rules are written to be concise and machine-readable for agents and to match typical Kotlin/Ktor idioms used in the project.

Packages and files
- Package names: use all-lowercase dot-separated identifiers. Example: `package be.endevops`.
- One top-level public class or object per file when it improves clarity. Small related helper functions may share a file.
- File names: use PascalCase for Kotlin files that contain a class/object with the same name (e.g., `Application.kt`), otherwise use a short descriptive name (e.g., `Routing.kt`, `Serialization.kt`).

Imports
- Avoid wildcard imports. Always import classes explicitly.
- Group imports by standard library, third-party libraries, and project packages.
- Prefer explicit imports (Tools/agents should not introduce wildcard `*` imports).
- Keep import ordering stable (e.g., alphabetical within groups) to minimize churn.

Formatting
- Follow Kotlin official code style: `kotlin.code.style=official` (see `gradle.properties`).
- Use 4-space indentation (match project default IDE settings) and no trailing whitespace.
- Line length: prefer wrapping before ~120 characters for readability in reviews and diffs.
- Use expression-bodied functions for short single-expression functions when it improves clarity.

Naming conventions
- Packages: lower_case (dot-separated), e.g., `be.endevops`.
- Classes/Objects/Interfaces/Enums: PascalCase (e.g., `Application`, `UsersSchema`).
- Functions and properties: camelCase (e.g., `configureRouting()`, `configureMonitoring()`).
- Constants: `const val` in UPPER_SNAKE_CASE when top-level or inside objects/companion objects (e.g., `const val DEFAULT_PORT = 8080`).
- Database/table/schema objects: PascalCase for object/companion names representing schemas; column or field names in models should be camelCase.

Types & nullability
- Prefer explicit types for public functions and top-level properties. For private/local variables, rely on Kotlin type inference when the type is obvious.
- Use nullable types (`T?`) only when absence is a valid state; prefer non-null types otherwise.
- Avoid platform types (`!!`) unless you have validated the value; prefer safe calls `?.` and `?:` defaults.
- Use `sealed class` or `enum` for closed sets of possible values or error/result variants.

Functions & parameters
- Keep functions small and single-responsibility. If a function grows > 60 lines, split it.
- Prefer immutable parameters (use `val`). Do not mutate input parameters.
- Use default parameter values for optional arguments instead of overloaded functions where it improves readability.

Coroutines and concurrency
- Use structured concurrency and prefer `suspend` functions for asynchronous work.
- Avoid launching global coroutines (e.g., `GlobalScope`). Use properly-scoped coroutine contexts (e.g., application lifecycle or Ktor contexts).

Error handling
- Favor typed errors and explicit handling over swallowing exceptions.
- For recoverable errors return `Result<T>` or a sealed `Either`/`Result` type; for unrecoverable errors throw exceptions.
- Avoid broad `catch (e: Exception)` blocks. If catching `Exception`, log and rethrow unless intentionally swallowing with a clear comment.
- Use logging (the project uses Logback) to record errors with context. Avoid leak of sensitive data in logs.
- Validate external input (JSON, DB results) and fail fast with meaningful messages.

Logging
- Use structured messages and include context fields where helpful. Prefer `logger.info("action={}, id={}", action, id)` style.
- Do not log large payloads or secrets. Sanitize or truncate sensitive fields before logging.

Ktor-specific guidelines
- Keep routing in `Routing.kt` and use extension functions to attach routes, following the existing pattern: `fun Application.module()` calls configuration functions.
- Use Ktor testing utilities for HTTP tests (`testApplication` and `client.get/post` in `src/test/kotlin`).
- Use `ContentNegotiation` and `kotlinx.serialization` for request/response bodies. Prefer data classes annotated with `@Serializable` in `Serialization.kt`.

Database & Exposed guidelines
- Use transactions for DB work and keep transactional scope small.
- Keep schema declarations in `UsersSchema.kt` (or similarly named files).
- Map DB types to Kotlin types explicitly and avoid nullable columns unless appropriate.

Testing guidelines
- Unit tests: keep them fast and isolated. Mock or use in-memory DBs (H2) for small integration tests.
- Integration tests: use `testApplication` to spin up the application and exercise HTTP routes; keep them stable and deterministic.
- Name tests clearly: `className_methodUnderTest_expectedBehavior` or use descriptive test method names as in the existing `ApplicationTest.kt`.
- When adding tests that require environment variables or external services, provide a local test double or document required setup in README.

Agent behavior and file edits
- Agents must run the Gradle wrapper `./gradlew` for build/test tasks to ensure consistent tool versions.
- When making changes that affect many files (e.g., bulk imports or formatting), prefer minimal diffs: group logically related edits into a single change set.
- Before editing a file, read it. Avoid blind replacements that may break coding conventions or tests.
- Do not change public APIs without updating callers and adding tests.
- If adding a new dependency, update `build.gradle.kts` and ensure `./gradlew build` and `./gradlew test` succeed locally.

Cursor/Copilot rules
- This repository has no `.cursor` or `.cursorrules` directory and no `.github/copilot-instructions.md` (checked at workspace root). Agents should not assume any project-level cursor or Copilot overrides.

When to ask for human review
- Large refactors affecting public APIs, database schema migrations, or deployment configuration.
- When adding new build tooling (linters, formatters) that change CI behavior.
- Any change that touches secrets, CI configs, or the publishing/packaging pipeline.

Where to find useful files
- Build file: `build.gradle.kts`
- Gradle properties (style hint): `gradle.properties`
- Application entrypoint: `src/main/kotlin/Application.kt`
- Routing, serialization and schema helpers: `src/main/kotlin/Routing.kt`, `Serialization.kt`, `UsersSchema.kt`
- Tests: `src/test/kotlin/ApplicationTest.kt`

Contact & process
- When in doubt, prefer conservative changes and create a PR with a clear summary and link to failing/passing tests.
- Run `./gradlew test` locally after changes and include test output in the PR description if relevant.
